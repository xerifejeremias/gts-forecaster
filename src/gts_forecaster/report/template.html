FAQ: methods, assumptions and design decisions

For data scientists and technical reviewers. Values in bold are the settings of this report's run; module paths are under src/gts_forecaster/, settings in config/. The full decision log, with dates, is OVERVIEW.md in the project.

Settings used for this report

Which settings produced the numbers in this report?

The forecast uses the selection made by the last backtest; where its settings differ from this run's (e.g. the metric or top_n), the selection's values decided which models are used. Where: config/default.yaml, config/frequency_profiles.yaml, registry/<frequency>/selection*.json (meta).

Input data and preprocessing

What does the pipeline assume about the input data, and what is checked?

Long format: one row per series and date, with an id, a date, a numeric target, the configured explanatory columns and optional static (identifier) columns. A strict contract runs right after loading (pandera + plain pandas) and stops the run with nothing written on any breach:

  • exactly the expected columns (extra columns are dropped and logged by default, extra_columns: ignore); numeric target and explanatory columns; dates without time zone; no nulls in id or date; no infinite values;
  • no duplicated (id, date) rows; dates aligned to the frequency (pandas MS);
  • static columns are text with exactly one non-empty value per series (codes like 0042 keep their zeros).

Input names are mapped to uuid, date, target (input_columns), and right after the contract renamed to the Nixtla convention unique_id, ds, y, used everywhere downstream. Inputs can be CSV, Parquet or a SQL query (SQLAlchemy URL from an environment variable, so no password is stored in the config).

Where: contracts/input_schema.py, contracts/static_checks.py, contracts/frequency_checks.py, io/loaders.py, columns.py.

How are missing periods and gaps handled?

A period is missing when its row is absent or its target or an explanatory value is null. Rules per run of consecutive missing periods in one series (threshold max_fill_periods = 3):

Where the gap isShort gap (≤ threshold)Longer gap
Inside the serieslinear interpolationfallback forecast
At the end (series stops early)forward fill up to the common cutofffallback forecast

Fallback series never reach a model or the backtest; their forecast is the last real observed value (never a filled one) or 0 (fallback = last_value). Filled rows carry an internal is_filled flag: they are never scored in the backtest and never flagged as outliers. The contract is then checked again: no nulls, no gaps, all series end on the same date.

Known side effect: interpolation applies to every value column, so a binary explanatory column (e.g. a promo flag) can become 0.5 inside a filled gap.

Where: cleaning/missing.py, data_preparation.py.

Why do all series share one cutoff date?

The forecast origin is the latest date in the data, common to all series: short end-gaps are forward-filled to it, longer ones send the series to the fallback. One origin keeps the horizon dates identical across series, which the platform output, the totals in this report and the global models (one prediction call for all series) rely on. A series that stopped reporting long ago is therefore not forecast by a model, by design.

Where: cleaning/missing.py, splitting.forecast_split.

What happens to very short, brand-new or not-yet-backtested series?
  • Fewer than 3 observations (min_series_length of the frequency profile): last observed value for the whole horizon, with a warning. Decided 2026-10-11: before, one new product stopped the whole run at the contract.
  • Too short to be backtested (no fold in which the reference model naive could be scored): a fixed ensemble of the first 2 models of naive, seasonal_naive, drift that the series has enough data for, equally weighted. Seasonal naive needs one full season, so very short series get naive + drift.
  • New since the last backtest (no entry in the selection): the same short-series ensemble, with a warning, until the next backtest (added after the 2026-10-12 code review; before, such a series stopped forecast and train).

Where: cleaning/missing.split_short_series, selection.short_series_choice, selection.add_missing_series.

What date convention is assumed?

A date marks the start of its period (2024-03-01 = March 2024; weekly dates start a 7-day week). This only matters for the calendar features (days, business days, holidays in the period). If the data stamps period ends, set calendar.period_anchor: end in config/features.yaml. Still to be confirmed against the real data.

Where: features/calendar_features.py.

Are negative values allowed?

In the input, yes: real volume data can have restatements or loadings below zero, and they are modelled as they are. The forecasts are not: see "Why are negative forecasts set to 0?". Models that need positive data handle it locally: Tweedie boosting scales each series to 0..1 first, and a multiplicative-season ETS falls back to naive on a series with values ≤ 0.

Outliers

How are outliers detected?

Method mad (outlier_method = mad), per series, on the target only:

  1. Seasonality removed first when the series has at least three full seasons away from its ends: the typical offset of each season position from a rolling-median trend is subtracted, so normal seasonal peaks are not flagged.
  2. Local reference: each point is compared with the median of its two neighbours on each side, excluding itself. This follows trends and smooth cycles and is not pulled by the outlier itself.
  3. Robust scale: a point is an outlier when its residual is more than 5 robust standard deviations (1.4826 × MAD of the residuals) from zero (outlier_threshold). 5 is deliberately high: only severe outliers are touched.
  4. Iterative passes: only the most extreme point of a cluster of nearby candidates is flagged per pass; after replacing it the series is scored again, so the neighbours of one huge spike are not flagged too.

Validation on synthetic data: no false positives on yearly/monthly, 2-3 points on weekly/daily; injected 6-sigma spikes were found in 87-98% of cases.

Where: cleaning/outliers.py.

What is done with a flagged point, and why clip by default?

outlier_action = clip. Options:

  • clip (default): the value is moved to the threshold bound it crossed (expected value ± threshold × robust spread). A very high value stays high, just no longer extreme. Rationale: in volume data a spike is usually a real event (promotion, stock-up), not an error, so removing it entirely would bias the level down; clipping keeps the direction but limits its leverage on the fit.
  • interpolate: linear between the nearest unflagged neighbours (treats the point as an error).
  • median / mean of the series' unflagged values.

The replacement keeps the series regular (no gaps), which every model needs.

Which safeguards stop the outlier step from damaging a series?
  • The first and last two points are never flagged: at the edges a recent jump cannot be told apart from a level change, and the last points matter most for the forecast.
  • Periods filled by the missing-data step are never flagged.
  • Series with fewer than 8 observations are left alone.
  • If more than 10% of a series would be flagged (outlier_max_share), the series is left unchanged with a warning: that pattern is a level shift or a regime change, not outliers.
Is outlier cleaning a source of leakage? Are the test windows cleaned?

No and no. Cleaning runs on training data only, separately inside every backtest fold using only that fold's history, and once more on the full history for the forecast. Test windows are scored against the raw actuals (decided at design time): a model is judged on what really happened, spikes included. The forecast sanity check reuses the same robust scale (see "Forecast checks").

Reviewable output: backtesting/<f>/backtest_outliers_*.csv (per fold) and outputs/<f>/outliers.csv (forecast run), columns uuid, ds, y_raw, y_clean, score.

Features and leakage

Which features do the models use?

Features are opt-in per model. Statistical models (StatsForecast), Chronos and Prophet/Orbit build what they need themselves. The MLForecast models (LightGBM, XGBoost, random forest, ridge, lasso) get:

  • Target lags and rolling statistics built by MLForecast. Default lags 1, 2, 3 and one season; rolling mean and std over 3 and one season. Per frequency (decided 2026-10-11 from a backtest of the default vs a denser short-term set, adopted only where it clearly won): daily lags 1-7, 14, 21, 28 and windows 7, 28 (all ML models, 6-16% better); yearly trees lags 1-5, windows 3, 5. Season length here: 12.
  • Calendar features (known for any future date): days and business days in the period, holidays, weekday counts, month, quarter, week of year, Fourier terms (order 2) of the yearly cycle (and weekly for daily data).
  • Static features for the *_static models: ordinal codes of each identifier column, group statistics (mean, relative level, number of series per group) and series descriptors (mean, std, trend, seasonal strength).
  • Target scaling per series before training (local_standard), so one global model can serve series of very different levels; Tweedie settings use local_minmax because Tweedie needs a non-negative target.

A series needs max(largest lag, longest window + 1) + 3 observations for an ML model (monthly default 16).

Where: models/mlforecast_adapter.py, features/, config/features.yaml, ml_features in config/frequency_profiles.yaml.

How is look-ahead leakage prevented?
  • One place decides train vs test: splitting.py. Everything downstream is a function of the cutoff: outlier cleaning, feature building, static group statistics and target scaling are all computed inside each fold from that fold's history only.
  • Multi-step forecasts: MLForecast predicts recursively (each prediction is fed back as the next lag). For feature sets used by direct models, usable_at_step(h) keeps only features known at step h (a lag k is only usable when k ≥ h); unknown ones are NaN. A test checks that the future features equal the history features wherever they are known, and that a row never sees its own value.
  • Explanatory variables: only columns declared as known in the future are used (next question). In the backtest the actual values of those columns in the test window are used, since by definition they are known in advance.
  • Static codes come from the full static table (stable integer codes across folds); they carry no target information.
  • Chronos is pretrained on public data; production data is private, so test-set contamination through pretraining is not a concern (an explicit assumption of the model choice).
Are the explanatory variables (price, promotions, ...) used?

Only those whose future values you supply. Default (decided 2026-10-05): none is known in the future, so models work without explanatory variables. Known columns in this run: none. Declaring one (known_future_columns + a future-values file) makes it a regressor for MLForecast, Chronos-2, Prophet and Orbit, in training and forecast. Unknown columns are never used: using them would need forecasting them first, which is out of scope.

Where: features/known_future.py.

How are holidays and business days defined?

Weekends are Saturday and Sunday. Holidays are the dates listed in calendar.extra_holidays plus, optionally, a country's public holidays (calendar.holiday_country, needs the holidays extra). The default has no country, so only listed dates count: set the market's country when real data arrives.

Where: config/models.yaml, models/.

Which models were considered and deliberately left out?
  • NeuralForecast (NHITS, NBEATS, TFT, PatchTST): want a GPU.
  • TimesFM 3.0: weights under a non-commercial licence; the production use is commercial.
  • TimesFM 2.5, Toto, Moirai-2: pin old NumPy or other versions that conflict with the stack.
  • TiRex: licence to be checked, original version univariate only. Kronos: built for financial candlestick data. TinyTimeMixer, Lag-Llama: weaker benchmark results.

Any of them can be added later as an adapter plus a catalog entry.

Why are there so many LightGBM, XGBoost, random forest, ETS and Theta variants?

The user asked for 8-10 boosting settings and 4-5 forests per family (shallow, regularised, deep, L1 loss matched to MAE, Tweedie for volumes, with/without static features, daily lag sets) and fixed ETS/Theta forms (damped, no trend, additive/multiplicative season; standard/optimised/dynamic Theta). skip_frequencies keeps each to the frequencies it suits (e.g. deep trees only on weekly/daily, where there are enough rows).

Evidence so far: each set wins more series in the backtest but gives no out-of-sample gain on the synthetic data (fair hold-out within ±1 WAPE point). With 2-3 folds per series, many similar candidates mean some win by luck (selection overfitting). Decided by the user (2026-10-11/12): keep all competing until real data is available, then prune. The Models tab lists models never in any series' top 3 as removal candidates.

Why does AutoARIMA not run on daily data, and fit non-seasonally on weekly data?

Run time. On weekly data, seasonal ARIMA with season 52 had not finished one fold after 24 minutes, so above a season length of 24 AutoARIMA fits a non-seasonal model (AutoETS does the same internally). On daily data AutoARIMA took 61% of the backtest time while in 4 of 55 selections, with the same hold-out accuracy without it (decided 2026-10-11). AutoTheta and its variants use only the last 5 years of daily history for the same reason.

How are the Chronos foundation models used?

Zero-shot: fit only stores the last 1,024 observations per series (max_context) and loads the weights (downloaded once from Hugging Face, cached across folds). The point forecast is the median of the predicted distribution. Chronos-2 receives known future covariates if any are declared; Chronos-Bolt is univariate. Minimum history 5 observations. CPU by default.

Where: models/chronos_adapter.py.

What happens when a model fails?
  • Backtest: a crashing model is isolated per fold and recorded (backtest_failures_*.csv); the others continue (on_model_error = skip; raise stops instead).
  • StatsForecast silently replaces a series it cannot fit with a naive forecast; the adapters log these series (e.g. multiplicative-season ETS on series with values ≤ 0).
  • Forecast: if a selected model fails, it is dropped from that series' ensemble and the remaining weights are rescaled; an error is raised only if none is left.
  • Prophet/Orbit failing on every series is treated as a setup problem and stops the run rather than returning last values labelled as the model.

Backtest and model selection

How is the backtest designed?
  • Rolling origin with 3 folds (n_folds), cutoffs 12 periods apart (backtest_step; default = the horizon, so test windows do not overlap), horizon 12.
  • Each fold: a fresh clone of every model, fitted only on series with at least the model's minimum history before the cutoff; early folds therefore cover fewer series (n_folds per series is in backtest_scores.csv).
  • The forecast floor (0) is applied to every model's predictions before scoring, so the scores judge what would really be delivered. Filled periods are not scored.
  • Every backtest writes a new, never-overwritten file of all forecasts vs actuals (backtest_forecasts_*.csv), which feeds the Accuracy and Models tabs.

Where: splitting.backtest_splits, evaluation/backtest.py.

Which metric ranks the models, and why?

metric = mae (options: mae, rmse, mape, smape, wape, mase). Ranking is per series, so a scale-dependent metric such as MAE does not mix levels across series, and it is robust to occasional spikes compared with RMSE. MAPE is undefined at zero actuals (NaN) and asymmetric, which rules it out for volumes that can be zero. MASE scales by the in-sample seasonal-naive error. This report's Accuracy and Models tabs default to WAPE because they compare totals across series, where a scale-free metric is needed.

Where: evaluation/metrics.py.

How is the model (or ensemble) chosen for each series?
  1. Reference folds: the folds in which naive (the model needing the least data) was scored. Every model competes only on those folds and must have a valid score on all of them, so no model gains from being scored on easier or fewer folds.
  2. Models are ranked by their mean score over those folds (ties go to the model listed first in models.yaml).
  3. The best 3 (top_n) form the series' own mix, weighted equal (ensemble_weights: equal or inverse error).
  4. The final weights follow the selection rule (next question).
  5. No model with a valid score: naive.

The choice is saved to selection_fast.json / selection.json: human-readable, editable, and an entry with "locked": true survives the next backtest (manual overrides).

Where: selection.py, registry.py.

What is the "blend" selection rule, and why is it the default?

selection_rule = blend, blend_share = 0.5. Each series' final forecast is half its own top-3 mix and half a common mix: the 3 models with the lowest error over all series together (each model's error summed over series, relative to naive's on the same series; a model must cover at least half of the backtested series). Overlapping models add their weights, so an entry holds up to 6 models.

Why: with 2-3 folds per series the per-series winner is noisy. Seven rules were compared offline on saved backtests with an expanding window (choose on earlier folds, test on the next): per-series top 3 / top 5 / best per family / global shortlist / common mix only / median instead of mean / blend / own mix only if 5% better. The common mix alone was best on average but worse on weekly and hurt more single series; the blend was never worse than the per-series rule. Fair WAPE per_series → blend: yearly 17.0% → 15.9%, monthly 13.3% → 12.8%, weekly 26.5% → 26.5%, daily 23.9% → 23.3% (synthetic data). Adopted 2026-10-12.

Why ensembles instead of the single best model?

Averaging cancels part of the individual models' errors and reduces the variance of a noisy per-series choice. In the fair hold-out check (choose on earlier folds, score on the last fold never seen by the choice), the top-3 ensemble beat both naive and the single best model at every frequency:

How much can I trust the backtest accuracy in this report?

The backtest view of the final forecast is optimistic: the selection was chosen on the same folds it is shown on. The individual models' backtest scores are honest out-of-sample numbers, but the best of dozens of candidates on 2-3 folds per series is biased upwards by the selection itself. For an unbiased estimate use scripts/holdout_check.py (replays the selection on earlier folds and scores the last one), and, over time, the Accuracy tab's Live view, which scores forecasts that were really delivered.

What are selection_fast.json and selection.json?

One backtest scores every model once and writes two selections: the best among the fast models only, and the best among all models scored (including Prophet/Orbit if the backtest ran with --no-fast-only). A model's score does not depend on which others compete, so no second backtest is needed. The forecast and this report read the fast one while fast_only is on. A fast-only backtest never overwrites a selection.json in which the slow models really competed.

Forecast and output

Are the models refitted for every forecast?

forecast_mode = frozen_selection. frozen_selection (default): the selection is kept, the selected models are refitted on the newest data at every run. frozen_models: train saves fitted models; the forecast loads them and passes the newer history without refitting where the model supports it (baselines, MLForecast regressors, Chronos); others are refitted with a warning. On monthly data both modes gave identical forecasts. Known gap: a changed features.yaml is not detected in frozen-models mode.

Only the models named in the selection are run (forecast_models = selected); all runs every candidate, for the per-model lines of the Forecast tab.

Why are there no prediction intervals?

A decision of the project owners (2026-10-05): the receiving platform takes point forecasts only. Intervals would also need calibration across very different model families and a rule for combining them in an ensemble; none of that is built.

Why are negative forecasts set to 0?

The target is a volume (decided 2026-10-05): forecast_floor = 0. The floor is applied to every model's prediction in the backtest (so selection judges what is delivered), to every model column and to the final ensemble; the output contract rejects any value below it. The input history keeps its negative values.

Which sanity checks run on the final forecasts?
  • outlier: a forecast step more than 5 robust standard deviations from its neighbouring steps (spread taken from the history, floored at 1% of the series' median level).
  • total_change: forecast total vs the same number of periods before the cutoff, more than 3× up or down.
  • start_jump: the first 3 steps more than 3× off both the last 3 actuals and the same periods a season earlier.
  • zero: an all-zero forecast after non-zero recent history.

forecast_check_action = warn (flag, still deliver; raise stops before writing anything). Flags appear in the Forecast tab and in forecast_checks.csv.

Where: forecast_checks.py.

What exactly goes to the platform?

forecast_output.csv, long format: uuid, date, <static columns>, forecast, one row per series and horizon date, final forecast only. An output contract checks columns and order, no empty or non-finite values, no duplicates, every expected series present with exactly the horizon dates, identifiers constant per series, nothing below the floor. Column names can be changed without code (output_rename).

Where: output.py, contracts/output_schema.py.

Code design and reproducibility

What are the main design principles of the code?
  • Config-driven: frequency, horizon, metric, model set and selection rule are config changes, never code changes.
  • Cutoff-driven: one split function; cleaning and features are functions of the cutoff (no leakage by construction).
  • One model interface (models/base.py: BaseForecaster): fit(train) / predict(future) on a panel, where future carries horizon_step, so no model knows the horizon or frequency. Third-party libraries sit behind adapters and are imported only at fit time. A new model = adapter + catalog entry; backtest, selection, report and timings pick it up automatically.
  • Contracts stop the run: input, model frame, selection and output each have a contract; a breach raises DataContractError and nothing is written. Registry files are written atomically.
  • The report never runs a model: it only reads saved files; it is one self-contained HTML file (no server, no external libraries), with the same data in forecast_report_data.json for a future web app.
Is a run reproducible and auditable?

run-pipeline (the production entry point) records every run in runs/<frequency>/<run id>/: run.log, manifest.json (resolved settings, step timings and errors, Python and library versions, an input fingerprint: SHA-256 and line count for files, query hash for SQL), a copy of the config folder and of every output. Seeds are fixed (boosting and forest regressors; Orbit 8888); the dependency versions are locked in poetry.lock. A failing step is recorded, later steps are marked skipped, the exit code is 1.

Why do StatsForecast models run on one core while the tree models use all cores?

On Windows, StatsForecast's n_jobs > 1 starts new processes on every fit (~13 s each): monthly fits became 7-25× slower and the test suite 17 min instead of 3.5. LightGBM, XGBoost and scikit-learn use threads, with no start-up cost: all cores gave 1.2-2.5× speed-ups. Revisit StatsForecast parallelism with many long real series.

How is the code tested?

About 660 pytest tests: unit tests per module and contract tests that prove each rule can fail (valid and invalid inputs), plus leakage tests on the features. The report's JavaScript has no unit tests; it is checked in a headless browser (scripts/check_report_in_browser.py: JS errors, phone width, every button). The library adapters were first tested against stand-ins and then confirmed on the real libraries in the first laptop run (2026-10-11).

Known limitations and open points

What has not been validated yet?
  • All results so far are on synthetic data (trend + seasonality + noise, three predictability tiers). Real data (promotions, intermittent volumes, restatements) may favour different models; the pruning of variants, the folds, the outlier threshold (5) and the 10% safeguard are to be re-judged on it.
  • Date convention (period start vs end), country holidays and the platform's column names are still to be confirmed.
  • Selection noise: with few folds per series, many similar candidates overfit the choice; options noted are more folds, a minimum margin to switch models, or fewer candidates.
  • Static group statistics include the series itself (no leave-one-out), so a group with very few series is close to the series' own history.
  • No intermittent-demand models (e.g. Croston/TSB) yet; zeros are handled by the general models and the floor.
  • Frozen-models mode does not detect a changed features.yaml.
